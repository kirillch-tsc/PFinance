# PFinance: project rules

Эти правила обязательны для продуктовых, UX/UI- и технических изменений PFinance.

## 1. PFinance заменяет Excel

Приложение создаётся как замена текущей Excel-таблицы. Оно должно сохранять нужный финансовый учёт, но устранять неудобство таблицы на телефоне. Нельзя буквально копировать Excel в веб-интерфейс.

## 2. Простота — ограничение продукта

Интерфейс должен оставаться простым на всех этапах. Новая функция допустима, только если она решает конкретную проблему пользователя и не ухудшает главный сценарий.

## 3. Не добавлять функции «на будущее»

Нельзя добавлять экраны, поля, настройки, абстракции или интеграции только потому, что они могут понадобиться. Изменение должно обслуживать текущий согласованный этап.

## 4. Не менять структуру без согласования

Без явного согласования нельзя менять:

- основные пользовательские сценарии;
- состав и назначение основных разделов;
- модель данных и финансовые правила;
- навигацию;
- технологическую основу проекта;
- согласованные UX/UI-принципы.

Предлагаемое структурное изменение нужно сначала описать: какую проблему оно решает, что меняет и какие имеет последствия.

## 5. Защищать главный сценарий

Главный сценарий PFinance:

> Быстро добавить операцию и увидеть текущее состояние финансов.

Любое изменение нужно проверять на влияние на этот сценарий. Если оно делает ввод дольше, усложняет восприятие или отвлекает от ключевых показателей, его не нужно принимать.

## 6. Правило минимального изменения

В каждой задаче нужно:

1. менять только файлы, необходимые для текущей цели;
2. не совмещать задачу с несвязанным рефакторингом;
3. не менять поведение, контракты или UX без явной необходимости;
4. фиксировать заметные продуктовые решения в документах.

## 7. Проверка перед слиянием

Каждый pull request должен подтверждать:

- какую текущую задачу он решает;
- что в diff нет несвязанных изменений;
- что главный сценарий не ухудшен;
- что новая сложность оправдана;
- что изменение не противоречит `docs/UI_REFERENCE.md`.
