# PFinance: decision log

Журнал хранит принятые продуктовые, UX/UI- и технические решения. Новая запись добавляется только после согласования. Старые записи не удаляются: изменившееся решение получает статус «заменено» и ссылку на новую запись.

Статусы: `принято`, `заменено`, `отклонено`.

## D-001. PFinance заменяет Excel

- **Дата:** 2026-07-22
- **Статус:** принято
- **Контекст:** семейный учёт ведётся в таблице, которую неудобно заполнять с телефона.
- **Решение:** создать отдельное веб-приложение, которое сохраняет нужный учёт, но не копирует Excel буквально.
- **Следствие:** каждая функция должна быть оценена по сравнению с удобством и простотой заменяемой таблицы.

## D-002. Mobile-first как базовый подход

- **Дата:** 2026-07-22
- **Статус:** принято
- **Контекст:** операции должны добавляться в момент траты, поэтому основное устройство — телефон.
- **Решение:** проектировать и проверять интерфейс от мобильного сценария к десктопному.
- **Следствие:** навигация, формы, touch-targets и иерархия информации сначала должны работать на узком экране.

## D-003. Главный пользовательский сценарий

- **Дата:** 2026-07-22
- **Статус:** принято
- **Контекст:** приложение не должно превращаться в перегруженную учётную систему.
- **Решение:** защищать один цикл: быстро добавить операцию и сразу увидеть текущее состояние финансов.
- **Следствие:** функция, которая не улучшает ни одну из частей этого цикла, не входит в базовый scope.

## D-004. Четыре основных раздела

- **Дата:** 2026-07-22
- **Статус:** принято
- **Контекст:** для ввода, бюджета, общей сводки и параметров нужны разные режимы, но они не должны дублировать ввод.
- **Решение:** использовать четыре раздела: «Главная» для состояния финансов, «Операции» для ввода, «Бюджет» для лимитов и контроля их исполнения, «Настройки» для согласованных параметров приложения. В разделе «Бюджет» пользователь задаёт лимиты по категориям и видит их исполнение.
- **Следствие:** операция вводится один раз; балансы, потраченное и остаток бюджета рассчитываются из операций.

## D-005. Минимальная первая версия

- **Дата:** 2026-07-22
- **Статус:** принято
- **Контекст:** графики, сложная аналитика, планируемые платежи и прогнозы увеличивают сложность.
- **Решение:** не включать эти функции в первую версию без отдельного согласования.
- **Следствие:** первая версия сосредоточена на операциях, счетах, бюджетах и краткой сводке.

## D-006. Техническая основа

- **Дата:** 2026-07-22
- **Статус:** принято
- **Контекст:** проекту нужна современная mobile-first основа с production deployment.
- **Решение:** использовать Next.js, TypeScript, App Router, Tailwind CSS, ESLint и Vercel.
- **Следствие:** изменение стека или платформы развёртывания требует отдельного решения.

## D-007. Cash flow входит в базовую концепцию

- **Дата:** 2026-07-22
- **Статус:** принято
- **Контекст:** пользователю нужно видеть изменение состояния финансов за выбранный период.
- **Решение:** cash flow входит в базовую концепцию и равен доходам минус расходы за период.
- **Следствие:** переводы между собственными счетами не являются доходами или расходами и на cash flow не влияют.

## D-008. Постоянное хранилище MVP: SQLite через Drizzle

- **Дата:** 2026-07-23
- **Статус:** принято
- **Контекст:** сейчас приложение хранит все данные только в памяти браузера и при каждой загрузке страницы пересоздаёт их из захардкоженного набора строк, извлечённых из `Баланс.xlsx` (`src/storage/imports/balance-import.ts`). Реальные операции пользователя, введённые через интерфейс, теряются при обновлении страницы — это делает MVP непригодным для повседневного использования и блокирует финальный релиз. `docs/ROADMAP.md` не содержит отдельного этапа для перехода на постоянное хранилище, а чек-лист `docs/MVP_PLAN.md` (этап 11) исключал резервное копирование и импорт/экспорт из scope MVP — это решение уточняет тот пункт: базовое сохранение данных между запусками признано обязательным условием релиза, а не отдельной функцией импорта/экспорта.
- **Решение:** постоянное хранилище MVP — SQLite (файл `data/pfinance.db`), доступ к которому реализован через Drizzle ORM. Это единственный способ хранения по умолчанию для локального запуска и продакшена. `STORAGE_BACKEND=in-memory` сохраняется только для автоматических тестов и отладки и не является продуктовым режимом. Так как SQLite доступен только на сервере (файловая система Node.js), браузерная часть обращается к хранилищу через Route Handlers (`app/api/accounts`, `/api/categories`, `/api/transactions`) — контракты `src/storage/contracts/*` и бизнes-слой (`src/business/*`) при этом не меняются, меняется только реализация Storage и точка сборки в `app/`. Данные, извлечённые из `Баланс.xlsx`, больше не загружаются автоматически при каждом запуске — они доступны через отдельный однократный скрипт импорта.
- **Следствие:** каждый запуск приложения (после применения миграций) сохраняет операции пользователя между перезапусками. Отсутствие применённой миграции или недоступность файла базы — явная ошибка с понятным сообщением, а не молчаливый откат к пустому или неверному состоянию. Резервное копирование и восстановление сводятся к копированию файла `data/pfinance.db` (задокументировано в `README.md`). Budget-хранилище в это решение не входит: `BudgetStorageContract` пока не имеет ни одной реализации (in-memory или иной) и не используется в рантайме — переносить его в SQLite до появления реального потребителя преждевременно.
