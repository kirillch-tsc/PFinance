# PFinance: architecture

Документ описывает текущую техническую основу PFinance и границы будущей структуры. Он не разрешает добавлять модули заранее: любое расширение должно быть привязано к согласованному этапу из `docs/ROADMAP.md`.

## Текущий стек

- Next.js 16;
- React 19;
- TypeScript в strict-режиме;
- App Router;
- Tailwind CSS 4;
- ESLint;
- Vercel.

## Текущая структура

```text
app/
  globals.css       глобальные стили и подключение Tailwind
  layout.tsx        корневой layout и metadata
  page.tsx          стартовая страница

docs/
  ARCHITECTURE.md   техническая структура
  DECISIONS.md      журнал принятых решений
  PRODUCT.md        назначение и границы продукта
  PROJECT_RULES.md  обязательные правила изменений
  ROADMAP.md        единственный источник этапов
  UI_REFERENCE.md   направление интерфейса

.env.example        шаблон переменных окружения
README.md           запуск и обзор репозитория
NEXT.md             ближайшие рабочие задачи, без roadmap
```

## Границы текущего этапа

Сейчас проект содержит только стартовую страницу и документацию. Не реализованы:

- операции;
- счета;
- бюджеты;
- база данных;
- авторизация;
- продуктовая навигация;
- полноценный UI.

## Принципы размещения кода

Структура расширяется только по мере появления реального кода:

1. Маршруты, layouts и связанные с ними компоненты находятся в `app/`.
2. Повторно используемый код выносится только после фактического повторения, а не «на будущее».
3. Финансовые правила отделяются от UI, когда появятся реальные расчёты.
4. Серверный код, схема данных и способ авторизации не фиксируются до отдельного согласованного решения.
5. Новая папка или слой должны иметь текущего потребителя.

## Направление потока данных

После реализации базового учёта ожидается однонаправленный поток:

```text
ввод операции
        ↓
валидация и финансовые правила
        ↓
сохранение
        ↓
пересчёт состояния финансов
        ↓
обновлённое представление
```

Это направление фиксирует главный сценарий, но не определяет конкретную базу данных, API или механизм кэширования.

## Инварианты

- Mobile-first остаётся базовым подходом.
- Доход, расход и перевод должны иметь однозначную финансовую семантику.
- Перевод между счетами не меняет общий баланс.
- Балансы, бюджеты и cash flow рассчитываются из операций, а не вводятся вручную как дублирующие данные.
- Изменение структуры требует согласования и записи в `docs/DECISIONS.md`.

## Проверки

Каждое изменение кода должно проходить:

```bash
npm run lint
npm run build
```

По мере появления финансовой логики для неё нужны автоматизированные тесты.
